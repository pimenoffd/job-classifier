# Пояснительная записка: сервис сопоставления должностей с классификатором

## 1. Выбранный подход и его обоснование

Входные данные из 1С содержат преимущественно **структурный и орфографический шум**: опечатки (*«бетоононасоса»*), сокращения (*«маш.»*, *«инж. пто»*), сленг (*«бульдозерист»*), административные маркеры (*«вахта»*, *«ООО СтройМонтаж»*) и категории/разряды (*«5 разряда»*). Классификатор закрыт и содержит всего 56 записей.

Вместо недетерминированных нейросетевых решений выбран **детерминированный многостадийный пайплайн**:
1. **Доменная нормализация (`normalizer.py`):** удаление юрлиц, скобок, разрядов; раскрытие строительных сокращений; приведение профессиональных синонимов к канонической форме; исправление частых опечаток.
2. **Лексическое нечеткое сопоставление (`matcher.py`):** взвешенная метрика RapidFuzz:
   `Score = 0.5 · token_sort_ratio + 0.5 · ratio`
3. **Калибровка уверенности и OOD-фильтрация (`decision.py`):** пороговое разделение классов, отсечение непрофильных должностей (`Score < 0.55` → `НЕТ СООТВЕТСТВИЯ`) и выделение пограничных случаев на ручную проверку.

**Почему этот подход:**
* **Скорость и легкость:** <0.2 секунды на полный датасет, запуск на любом CPU без внешних сервисов и GPU.
* **100% воспроизводимость и прозрачность:** каждое решение трассируется до конкретного правила или лексического расстояния.
* **Эффект нормализации:** 300 входных строк схлопываются всего в **78 уникальных канонических форм**, сводя подавляющую часть сравнений к точным совпадениям (`Score = 1.0`).

## 2. Отвергнутые подходы

* **Эмбеддинги / плотный семантический поиск (Dense Retrieval):**
  * *Причина отказа:* плотные модели рассчитаны на семантическую неоднозначность в открытом словаре; здесь классов всего 56, а шум орфографический, а не семантический. На таком типе шума лексический поиск измеримо не слабее (см. раздел 3). Добавить эмбеддинги означало бы усложнить инфраструктуру (GPU, модель) без выигрыша в качестве.
* **LLM / локальные генеративные модели:**
  * *Причина отказа:* внешние API запрещены условиями ТЗ, а локальные LLM избыточны по памяти и времени инференса для фиксированного справочника из 56 позиций.
* **Классическое машинное обучение (TF-IDF + Ridge / CatBoost):**
  * *Причина отказа:* обучающая выборка (50 строк) меньше числа целевых классов (56) — обучение модели гарантированно привело бы к переобучению и потере редких классов.
* **Метрика `WRatio`:**
  * *Причина отказа:* в ходе калибровки выяснилось, что `WRatio` при пороге `0.55` пропускает 6 ложных срабатываний офисных должностей против 1 у комбинации `ratio + token_sort_ratio`.

## 3. Оценка слабых мест и работа с уверенностью

1. **Пограничные опечатки и ложные OOD (кейс `id 38 «МАСТЕР СТРОЙУАСТКА»`):**
   * Проблема двойная. Из-за опечатки и склейки слов лучший кандидат — `КЛС-009 Маляр строительный` (`score ≈ 0.545`), что чуть ниже порога `T_match = 0.55`, поэтому система отсеивает запись в `НЕТ СООТВЕТСТВИЯ`. Но даже если бы порог был ниже, ошибка бы не исчезла: семантически верный код `КЛС-047 Мастер строительных и монтажных работ` не лидирует среди кандидатов вообще — он делит 3–4 место с результатом `0.500`, заметно позади `КЛС-009`. То есть простое смягчение порога подменило бы честный отказ на уверенно неверный код. Система корректно маркирует запись `требует проверки: да`. Попытки грубо разбить склеенный префикс «строй-» ломали другие позиции, поэтому случай оставлен для явной валидации оператором.
2. **Случайное посимвольное сходство (кейс `id 113 «Переводчик»`):**
   * Из-за 7 совпадающих букв из 10 слово «Переводчик» набирает скор `0.737` против `КЛС-056 Проходчик`. Проблема решена списком базовых непрофильных стемов в `decision.py`. Если срабатывает OOD-стем при скоре ≥ `T_match`, система присваивает `НЕТ СООТВЕТСТВИЯ`, выставляет уверенность `0.000` и отправляет запись оператору (`требует проверки: да`), исключая тихую потерю данных.
3. **Интерпретация шкалы уверенности:**
   * Уверенность калибруется единообразно для обеих веток: при матчинге это сходство с эталоном (`Score`), при отсеве `НЕТ СООТВЕТСТВИЯ` — удаленность от границы приема. Сортировка `results.csv` по колонке `Уверенность` по возрастанию формирует готовую приоритизированную очередь для оператора.
4. **Ограниченность валидации на `labeled_sample.csv`:**
   * На 50 эталонных записях пайплайн показывает **Accuracy 100%**, однако эта выборка не содержит сложных склеек. Реальное качество системы точнее отражает прогон по 300 записям: **296 матчей приняты** (скор ≥ 0.55, уверенность в коде), **4 записи отправлены на ручную проверку** (1.3%: три из них — пограничные по уверенности, одна — id 38 с конфликтом скора и словаря непрофильной лексики).

## 4. Масштабирование на 3 млн записей и 10 000 классов

При переходе к Highload-масштабу архитектура трансформируется следующим образом:

```
[3M строк] ➔ [Дедупликация (Polars)] ➔ [Sparse BM25 + Dense FAISS/HNSW] ➔ [RRF / Cross-Encoder Rerank] ➔ [Decision Engine]
```

1. **Дедупликация на входе:** 3 млн записей из 1С схлопнутся в десятки тысяч уникальных нормализованных строк. Нормализация и дедупликация на Rust-бэкенде (`Polars`) устраняют >95% нагрузки до фазы матчинга.
2. **Индексация справочника (10k классов):**
   * Вместо полного перебора — разреженный индекс BM25 (по n-граммам и стемам) + векторный HNSW-индекс (`USearch` / `FAISS`).
   * Отбор кандидатов (Top-20) через Reciprocal Rank Fusion (RRF).
3. **Двухстадийный Reranking:** легкий Cross-Encoder (например, дистиллированный `ruBERT-tiny2`) точечно ранжирует Top-20 кандидатов.
4. **Инфраструктура:** потоковая обработка через Kafka/Celery, перенос словарей нормализации из кодовой базы в версионируемую БД (PostgreSQL/Redis).

## 5. План дальнейшего улучшения качества

* **Active Learning Loop:** операторы размечают только записи с флагом `требует проверки: да` (низкая уверенность или конфликт словаря со скором); подтвержденные правки автоматически пополняют словарь синонимов.
* **Подключение внешних отраслевых справочников:** парсинг синонимов и альтернативных наименований из ЕТКС и ОКПДТР для расширения канонических эталонов.
* **Мониторинг дрейфа данных:** отслеживание динамики доли записей, уходящих на проверку, как метрики появления новых нестандартных должностей.
